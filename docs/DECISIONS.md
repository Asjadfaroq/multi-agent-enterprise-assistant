# Decisions

Deviations from `BUILD_SPEC.md`, one line each.

- LLM provider is Anthropic via `langchain-anthropic` instead of OpenAI: agent model `claude-haiku-5-5`, judge model `claude-sonnet-5-5`, both set in `config.py` / `.env`.
- Embeddings are local `sentence-transformers` `BAAI/bge-small-en-v1.5` (384 dims) instead of OpenAI, so `chunks.embedding` is `vector(384)` and ingest needs no API key.
- Embedding helpers (`embed_texts`, `count_tokens`) live in `llm.py`, the spec's provider layer, because the tree has no embeddings module and both ingest and search need them.
- Chunks are measured in tokens from the bge tokenizer and capped at 500, under bge's 512-token input limit; no overlap, since chunks break on paragraph boundaries.
- `torch` is installed from the PyTorch CPU wheel index; the default wheel pulls several GB of CUDA libraries that local embeddings do not need.
- `python-frontmatter` parses the `acl`/`title` front-matter instead of hand-rolled YAML splitting.
- Langfuse runs as server v4 (current image) under a `langfuse` compose profile, so `docker compose up -d` starts only Postgres.
- Postgres is published on host port 5433 because 5432 is already taken by another local Postgres.
- The MCP server is one long-lived streamable-HTTP process (`uv run assistant-mcp-server`); the API passes the caller in an `X-User` header and `auth.py` resolves the role from the `users` table on every call. `X-User` is only trusted on requests that also carry `Authorization: Bearer <MCP_SERVICE_TOKEN>`; anything else gets 401, and both processes refuse to start without the token.
- Roles live in a `users` table (`auth.py` creates it, `scripts/seed.py` fills it), pulled forward from the spec's seed step because role lookup needs it now.
- `Plan`, `Draft` and `Review` live in `guardrails/schema.py` with the shared JSON parsing; the executor returns `Draft(text, citations)` so every node output is validated the same way.
- ACL-filtered search sets `hnsw.iterative_scan = strict_order` (pgvector 0.8) so the filter cannot make HNSW return fewer than k permitted chunks.
- The per-request stdio server spawn was replaced by the HTTP server: `/chat` for the same viewer question took 14.7–15.2 s with stdio and 4.4–5.4 s over HTTP, even though each turn now also makes the memory LLM call. (Earlier, one stdio session per request had cut a search from 8.4–9.7 s to ~0.5 s once open, but each request still paid ~6 s to start the server.)
- The embedding model loads with `local_files_only=True` once it is in the Hugging Face cache, so no process contacts the Hub; the MCP server loads it once at startup.
- MCP tools reach the nodes through LangGraph's runtime `context` (`AssistantContext`), so one compiled graph serves every user and tests inject fake tools the same way.
- Client-side session code lives in `graph/build.py` because the spec tree has no client module.
- Write tools pause with `interrupt()` inside a `request_approval` node rather than `interrupt_before`, so read-only tool calls never pause and the pause carries the proposed action.
- With one server for every caller, `list_tools` filters write tools by the caller's role, so viewers are never offered them; `create_ticket`/`update_ticket` still re-check the role in `auth.py` on every call.
- A rejected write ends the turn with a fixed "nothing was changed" answer instead of asking the model again, which re-proposed the same write in a live run.
- The turn's message history is append-only (reviewer feedback is a `name="reviewer"` message): Claude signs thinking blocks against earlier messages, and rewriting the executor prompt on revision made the API return 400.
- The reviewer sees the user's available tools, so true statements like "I cannot create tickets" are not rejected as ungrounded.
- The checkpointer is `AsyncPostgresSaver` (the graph is async), with the checkpointed Pydantic models (`Plan`, `Draft`, `Review`, `SearchHit`, `ProfileFact`) explicitly allowed in its serializer.
- `/approve` requires the approver to have ticket-write permission; the approved tools still run as the user who asked.
- `POST /ingest` is limited to the `manager` role (`require_ingest_permission` in `auth.py`); the caller comes from the same `X-User` header as the other endpoints.
- `/approve` takes a Postgres advisory lock on the thread id (`pg_try_advisory_lock(hashtextextended(thread_id, 0))`) and re-reads the thread under it: a concurrent decision gets 409 at once instead of waiting, and a decision on an already-resolved thread gets 409. A Postgres lock is used so it also holds across several API workers.
- Only one approved write runs per turn: a live run showed the model re-proposing the ticket it had just created, so further writes in that turn are refused without running or pausing.
- Long-term memory stores at most `MAX_PROFILE_FACTS_PER_TURN` facts (`preferred_language`, `team`) per turn via a `remember` node after the reviewer; the planner and executor both read them. The node lives in `memory/profile.py` and the fact models in `guardrails/schema.py`, because the spec tree has no memory node.
- Tracing uses the Langfuse v5 SDK (OpenTelemetry). User, session (thread id) and a `role:` tag are set with `propagate_attributes` around each graph run, because attributes set from inside a LangChain callback do not reach LangGraph's async node tasks. Each node span also carries `user`, `role`, `thread_id` and LangGraph's `langgraph_node` metadata.
- Langfuse exports only its own spans (`should_export_span=is_langfuse_span`): the Anthropic SDK emits an OpenTelemetry span per request, which Langfuse's default filter keeps, doubling every call's tokens and cost.
- Langfuse server v4 runs in events-only mode, so the legacy `GET /api/public/traces` endpoint is unavailable; traces were checked through `GET /api/public/v2/observations`.
- `scripts/demo.py` drives the HTTP API (not the graph directly), so a demo run exercises the same auth, approval and tracing path as real use.
- The service token is checked by a small ASGI wrapper around FastMCP's streamable-HTTP app (served with uvicorn) rather than FastMCP's built-in auth, which expects an OAuth authorization server; lifespan events pass through so the MCP session manager still starts.
- `scripts/demo.py` resets the tickets table to the sample tickets (`TRUNCATE ... RESTART IDENTITY`) before each run, so runs are repeatable and the demo ticket is always #5. It is meant for the demo database only.
- `api/app.py` keeps all three routes: `/chat` and `/approve` share the thread handling and `/ingest` is six lines, so there was no natural seam for route modules. The thread helpers (config, approval lock, response mapping) moved to `api/threads.py`, which the spec tree does not list.
- Prompt-injection checks run heuristics first and call the agent model only for text no heuristic caught: one call for the user's message and one batched call for all chunks of a retrieval, not one per chunk. When the classifier cannot return a valid verdict, the text is treated as an injection (fail closed).
- A poisoned chunk is dropped whole, including any legitimate text in it; the sample doc `vendor-onboarding-faq.md` is deliberately poisoned to prove the check, so its vendor-payment facts are never answerable.
- Guardrail hits are recorded as a marker span (`blocked_injection`, `dropped_poisoned_chunk`) inside the run's trace, carrying that tag. The tag is not on the trace's root span: the root starts before the guardrail decides, and Langfuse v5 has no call to add tags to a running trace. Filtering observations by the tag finds exactly one span per affected trace.
- PII is masked with presidio's email and phone recognizers plus a custom Saudi national ID/iqama pattern (10 digits starting with 1 or 2), called directly instead of through `AnalyzerEngine`, which would need a spaCy model. Masking happens on the user's message (`new_turn_state`), on every MCP tool result (wrapper in `server.py`), and in Langfuse's `mask` hook as a last line of defence.
- `Answer(text, citations, confidence)` replaced `Draft`. Every JSON-producing call gets one retry that shows the model its validation error; if the final answer is still invalid the user gets a fixed fallback (fail closed), and the API returns citations and confidence only for answers the reviewer accepted.
- `vendor-onboarding-faq.md` was cut to a short note about vendor payment dates, but it still ranks in the top 5 for some unrelated questions: with 14 chunks and k=5 every search returns over a third of the corpus, and viewers and agents can read only 6 chunks. Measured cosine scores leave no safe cut-off (relevant hits 0.589–0.828, unrelated hits up to 0.695), so no similarity threshold was added.
- Instead the retriever backfills: when the injection check drops chunks, one wider search (k + dropped) supplies the next-ranked chunks, which are screened too; drops among those are not refilled, so there is at most one extra search. `SearchHit` now carries `chunk_id` so the wider search can skip chunks already seen.
- The golden set uses an `expected_behavior` value per case instead of the spec's `must_refuse` flag, plus `key_facts` (quoted from the source docs) and `forbidden_in_answer` (restricted facts, raw PII or planted claims). `tests/test_golden_set.py` checks every case against the real docs, users, roles and PII detector. Write cases reference sample ticket ids, so eval runs must reset tickets first (`reset_sample_tickets`).
- Writes now need the user to have asked for one: the planner may plan `create_ticket`/`update_ticket` only for an explicit request, the executor only binds write tools the plan includes, and `request_approval` refuses any other write call without pausing. A live run had offered to open a ticket when the user only asked what to tell a vendor. The approval gate moved to `graph/nodes/approval.py`, which the spec tree does not list, to keep `executor.py` under ~150 lines.
- ragas 0.4.3 (the latest release) imports a module removed in langchain-community 0.4.2, so `langchain-community<0.4.2` is pinned as a uv constraint.
- ragas' `llm_factory` makes instructor force a tool call, which the judge model rejects, and it always sends `temperature`/`top_p`, which the installed Anthropic SDK rejects; `run_ragas.py` therefore builds the instructor client in `ANTHROPIC_JSON` mode and drops those two arguments. Answer relevancy uses the local bge embeddings.
- `scripts/` and `evals/` are packages run with `python -m` from the project root (`python -m scripts.seed`, `python -m evals.run_evals`), and pytest puts the root on `pythonpath`, so evals and tests import the seed data instead of loading files by path.
- The eval runner is split into `golden_cases.py`, `run_cases.py`, `behaviour.py`, `results.py` and `run_evals.py` next to the spec's `run_ragas.py`, `judge.py` and `regression_test.py`; `run_ragas.py` only scores, it does not run the graph.
- Each eval run resets the sample tickets and deletes threads still waiting for approval; each case clears its user's long-term memory and cases run one at a time, so no case sees another's tickets, pause or remembered language.
- Behaviour checks are deterministic (paused for the expected write, no pause, tickets unchanged, input blocked, no write requested, poisoned doc not in context, answer mostly Arabic, forbidden text absent), except whether a reply refuses or says "not found", which the judge decides through `behaviour_met`.
- Ragas runs on the factual, multi-hop, PII and Arabic cases; a case that retrieved nothing scores 0 for faithfulness and context precision. A case fails when a behaviour check fails, any judge score is below `EVAL_CASE_MIN_JUDGE_SCORE` (3), its faithfulness or context precision is below the gate, or scoring errors. The gates are the spec's (0.85, 0.80, 4.0, 100% behaviour) and were set before the first run.
- Arabic cases use digits as key facts, and answers are compared after mapping Arabic-Indic digits to ASCII.
- A request for a write the user's role lacks gets a fixed permission refusal from the executor without a model call, and the reviewer accepts it without one. In the eval run the model's own refusal claimed it had no document search tool, the reviewer rightly rejected that twice, and the user got the generic fallback.
- Viewers (and every role other than `agent` and `manager`) list and get only tickets they created. The policy lives in `auth.py` (`visible_ticket_creator`), it is applied in the tickets SQL, and a hidden ticket is reported exactly like a missing one.
- Embeddings switched from `BAAI/bge-small-en-v1.5` to `intfloat/multilingual-e5-small` (also 384 dims, so the table is unchanged) with e5's `query: ` and `passage: ` prefixes, because the English-only model could not retrieve English documents for Arabic questions. Models load with `local_files_only` once they are in the Hugging Face cache.
- `search_documents` fetches `RERANK_CANDIDATE_COUNT` (15) vector candidates and reranks them with `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` on CPU, so the injection check and backfill see the reranked top k; a hit's `score` is now the cross-encoder score. On this 4-core machine reranking adds about 4.9–6.8 s per search (vector search alone takes ~60 ms). Truncating pairs to 256 tokens measured 1.2 s and 10 candidates 1.4 s; neither is applied, because the spec asked for 15 full candidates.
- The answer prompt tells the model to ignore masked-data placeholders and never mention masked or personal data, after answers added unsupported lines such as "I did not use the iqama number you shared".
- Eval harness: ragas' output limit is raised to `EVAL_RAGAS_MAX_TOKENS` (8192) after three cases were cut off at 1024; the judge now sees tool results as well as document excerpts; progress lines are flushed so they appear when output is redirected.
- The 32 checkpoint threads still holding the pre-rename `Draft` model were deleted once with the checkpointer's `adelete_thread`; LangGraph refuses to deserialize the old class, which made the pending-approval scan log warnings.
- The reranker now scores `RERANK_CANDIDATE_COUNT` = 10 candidates, each question-passage pair cut to `RERANKER_MAX_TOKENS` = 256. On identical searches over the whole corpus the median search went from 2.34 s (15 candidates, 512 tokens) to 0.77 s; the 4.9–6.8 s reported earlier was measured on a busier machine.
- "Not found" is decided by the model through a required `answer_found` flag on `Answer`, not by a reranker score threshold: the lowest-scoring answerable golden question (-5.04) and the highest-scoring out-of-scope one (-5.65) are too close, and two out-of-scope questions score like relevant ones because nearby documents exist. When the flag is false the user gets one fixed sentence with no citations, and the reviewer accepts it without a model call.
- The executor is offered only the tools the plan names (search stays with the retriever), so a question the plan gives no ticket tools cannot set off a ticket lookup; in the last eval the weather question listed every ticket.
- Golden cases run concurrently, `EVAL_CASE_CONCURRENCY` (5) at a time, but never two cases of the same user at once, because each case clears that user's memory and may write to it. No case may change tickets, so a ticket change seen during a case is still a failure, though under concurrency it could come from another case.
- Each case's assistant output is cached in `evals/results/cache/` (ignored by git) under the golden-set hash and the code commit; uncommitted and untracked changes outside `evals/results` add a hash to the key, so edited code never reuses old outputs. `--fresh` ignores the cache.
- `--smoke` runs 12 cases covering every category and writes `evals/results/smoke.json` (ignored by git). The smoke run is gated only on coverage and behaviour, because twelve cases are too few for stable averages; the full run is gated on every threshold.
- CI (`.github/workflows/ci.yml`): ruff and unit tests on every push and on pull requests to main, with a pgvector service so the database tests run; one eval job runs the smoke eval on pushes to main and the full eval plus regression gate on pull requests to main. The job seeds the database, creates a per-job MCP service token, starts the MCP server in the background, caches `~/.cache/huggingface` keyed on `config.py`, and reads `ANTHROPIC_API_KEY` from repository secrets. Langfuse is not configured in CI, so evals there run untraced.
- The `committed_users` test fixture creates the `users` table itself; on a fresh CI database it failed because only the local seed had created it.
- The Langfuse callback handler runs inline (`run_inline = True`). LangChain otherwise hands a synchronous handler's events to a thread pool during async runs, so a span's start could be recorded after its end; Langfuse showed negative durations, for example on the chunk check under `retriever`. Batching and export stay in Langfuse's background thread.
- Tests blank the Langfuse keys through an autouse fixture: unit tests run from a shell with the keys exported had sent `ScriptedChatModel` traces to the real Langfuse project.
- CI runs ruff and unit tests on every push and pull request. Evals call the paid API, so they run only from a manual `workflow_dispatch` with a `smoke`/`full` choice, and the job stops at its first step with an error if `ANTHROPIC_API_KEY` is not set.
- When the turn retrieved chunks or read tickets, an answer marked `answer_found` must cite at least one of them; the reviewer checks this without a model call and sends an uncited answer back like any rejected draft. The eval adds a `cites_expected_source` behaviour check for answerable cases. An answer to a turn with nothing to cite, such as a greeting, is exempt.
- `python -m evals.run_evals --categories ...` re-runs only those categories and merges their results into `latest.json`; every case records the code version that produced it, so a merged file shows which cases are from an older run.
- The input guard and the planner run in parallel from the start of the turn, and an `apply_input_guard` join waits for both: it ends the turn on blocked input and discards the plan made for it. The planner only produces a plan (no tools), so seeing input that is later blocked does no harm. A join node is needed because a conditional edge on the planner cannot see the guard's verdict from the same step.
- The API replies as soon as the reviewer's verdict is final and lets the memory step finish in the background (`answer_turn` in `api/threads.py`), so the graph and the evals are unchanged. A `/chat` on a thread whose previous turn is still finishing gets 409, a failure after the reply is logged, and shutdown waits for unfinished turns before closing the checkpointer. Together with the parallel guard, the median warm `/chat` for omar's canary question went from 11.2 s to 8.7 s (5 runs each).
- The scripted test model answers the input guard's prompt with its configured verdict instead of the next queued reply, because the guard and the planner now ask it at the same time.
